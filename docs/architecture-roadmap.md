# SanA1 архитектурасы және даму жоспары

## Қандай мәселені шешеміз

FinTech ТЗ-дағы негізгі қауіп — бизнес ережесі, API шарты және қабылдау сценарийі әртүрлі мінез-құлықты сипаттауы. Мысалы, сатып алуды айға бөлу қағидасы сатып алу күніне сүйенеді, ал ресми кейстегі қабылдау кестесі келесі айдың санағышын өсіреді. Мұндай айырмашылық әзірлеуші мен тестілеушіге екі түрлі нәтиже береді. [Хакатонның бастапқы құжаты](https://github.com/BCC-HUB/ai-requirements-validator-task/blob/main/docs/requirements.md#L37-L65)

Өнімнің жұмыс циклі — файлды жүктеу → талаптар мен ақауларды қарап шығу → дәйексөзді салыстыру → автордың шешімін тіркеу → түзетілген мәтінді қайта тексеру → есепті сақтау. Толық аудитте шешімді ақау картасынан тіркеп, дәйексөзді редакторда ашып, түзетілген құжатты қайта тексеруге болады. Қайта тексеру бастапқы және жаңа аудитті салыстырады. Дәл жұбы табылмаған ақауды пайдаланушы бастапқы дәлелге қарап растайды. Автор шешімі, екі SHA-256 және қолмен расталған ақаулар JSON-ға кіреді.

Жергілікті ережелер режимі осы жұмыс жолын Gemini кілтінсіз орындауға мүмкіндік береді. Есепте ережелердің қамту шегі көрсетіледі. Салыстыруға бір режимдегі екі прогон алынады. Ресми тапсыруға толық Gemini аудитінің есебі қолданылады.

Басты беттегі демо виртуалды картаға арналған ТЗ-ны сол қойындыда ашады. Жергілікті аудит ай шекарасындағы сатып алу мен API арқылы баптауды өзгертуге қатысты екі ақауды көрсетеді. Қабылдау сценарийіндегі айды түзеткеннен кейін салыстыру API ақауының сақталғанын көрсетеді.

## Архитектуралық шешімдер

| Қабат | Қолданылатын стек | Қалай дамытамыз |
| --- | --- | --- |
| Құжатты оқу | `markdown-it-py`, `python-docx`, `pypdf` | Әр блок түрін, бөлімін, бастапқы ID-ін және координатын сақтаймыз. Markdown үшін жол, DOCX үшін шығарылған мәтін жолы, PDF үшін бет пен шығарылған мәтін жолы қолданылады. Күрделі PDF-ке арналған конвертерді бөлек бейімдегіш ретінде салыстырамыз. |
| Домендік тексеру | Python ережелері және бөлім бойынша контекст | API ережелері бір операцияның деректерін салыстырады. Келесіде байланысты функционалдық талап, ерекшелік және қабылдау сценарийінің ID-лерін сақтаймыз. Ресми кейстің әр парлы мысалында ереже ақаулы және түзетілген нұсқамен тексеріледі. |
| Контекстік тексеру | Gemini structured output және Pydantic | Бірінші өту талаптарды оқиды. Екінші өту құжат бойынша байланыстарды тексереді. Шығатын жауап берілген схемаға сай болуы және бастапқы блоктарға сілтеуі керек. Ұзын құжатқа бір операцияның контексін қосу тәсілі бірдей сынақтармен өлшенеді. |
| Есеп және интерфейс | Flask, CLI және бір JSON нәтижесі | Markdown архивке және тапсыруға, JSON автоматты тексеруге, веб дәйексөзді қарауға жарайды. Есептен құжат хэшін және нақты қолданылған модельді көруге болады. |
| Шешім мен қайта тексеру | Қазіргі редактор және нұсқаның SHA-256 хэші | Аудиттер критерий, сұрақ және бастапқы дәйексөздер бойынша салыстырылады. Дәл сәйкестік бірмәнді болса, жұп көрсетіледі. Өзге жағдайлар қолмен қарауға беріледі. Келесі кеңейту — тұрақты талап ID-ін және қабылдау сценарийінің байланысын қосу. |

Аудит интерфейсінде талаптарды бастапқы ID, есептегі ID, жол және мәтін арқылы табуға болады. Талап, ақау және дереккөз арасында екі жақты өту бар. Жергілікті ереже Markdown-дағы қабылдау кестесінің айқын берілген шарт, әрекет және нәтиже бағандарын тексереді.

Уақыт тексерісі орысша және ағылшынша міндетті талаптардағы «быстро» немесе «as soon as possible» сияқты тіркестерді қарайды. Талаптың өзінде уақыт шегі болса немесе уақытқа арналған нақты сілтемесі бар тармақта өлшем көрсетілсе, жергілікті ереже ескерту жасамайды. Шек жетіспесе, агент оны автордан сұрайды. Санау оқиғасы да көрсетілмесе, сұраққа сол оқиға қосылады. [NASA талаптар чек-парағы](https://www.nasa.gov/reference/system-engineering-handbook-appendix/) · [Requirements Smells зерттеуі](https://arxiv.org/abs/1611.08847)

## Жұмыс реті

1. **Ресми кейс және демо.** Нақты провайдермен бастапқы файлды жүргізіп, әр маңызды ақаудың сілтемесін қолмен салыстыру. Ай шекарасы, екінші push, оқу API-і, GET арқылы өзгерту, 200/400 және 403/404 бойынша шешімдерді көрсету. Бір файлдан веб пен CLI-де бірдей есеп құрылымын тексеру.
2. **Жалған белгілерді өлшеу.** Ақаулы, түзетілген және шатыстыруға оңай қарсы мысалдарды жинау. Әр тексеріске күтілетін ақау түрі және қажетті дереккөз жолдары белгіленеді. Сапа кестесінде recall, precision, дәйексөз дәлдігі және толық емес прогондар көрсетіледі. Провайдердің кідірісін жеке өлшеу.
3. **Автордың шешімі және қайта тексеру.** Қадамдар орындалды. Қайта тексергенде есеп критерийі, сұрағы мен дәлелі сәйкес ақауларды байланыстырады. Қазыға дайын демо үшін нақты провайдермен бір ақауды басынан аяғына дейін қайта жүргізіп, қабылдау сценарийіндегі айырманы көрсету.
4. **Құжат форматы мен провайдерді кеңейту.** Қазіргі парсермен және Docling-пен бірдей PDF нұсқаларын салыстыру. Модельді ауыстыру қажет болса, бірдей схема мен бірдей эталон арқылы әр нұсқаның сапасын, уақытын және қолжетімділігін жазу.

Жергілікті кодты тексеру командасы

```sh
python -m unittest discover -s tests -q
python app.py --evaluate
python -m tools.check_official_case "/path/to/requirements.md"
node --test tests/test_audit_comparison.mjs
```

Ресми кейс тесті алты бақылау жағдайының керек жолдарға сілтеуін тексереді. Әр жеке түзету қалған бес белгіні сақтауы керек. Барлық түзету бірге қолданылғанда ереже еш белгі бермеуі керек. Бұл сынақ ережелерге арналған және модель кілтін қажет етпейді.

Автоматты тесттердегі Gemini жауаптары бақыланатын имитациямен беріледі. Ресми файл бойынша нақты LLM сапасын тіркеу үшін серверге Gemini кілтін конфигурациялап, жаңа есептегі модель мен Git нұсқасын тексеріңіз.
